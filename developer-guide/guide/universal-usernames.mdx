This guide gets `happy` in your app resolving as `happy.brand.eth` in any ENS-aware wallet. You build one endpoint, save it in the Namespace App and set your resolver.

To learn why this works and what it changes for your users, read the [Universal usernames overview](/overview/universal-usernames).

## Prerequisites

- **An ENS name**, such as `brand.eth`, owned by a wallet you control.
- **An adapter.** A public HTTPS endpoint that reads a user from wherever your usernames live, such as your database, API or registry contract, and returns their profile. Step 1 covers it.

## Step 1: Build the adapter

### Request

You choose a base URL, such as `https://api.brand.example/ens`. For `happy.brand.eth`, Namespace calls:

```http
GET https://api.brand.example/ens/happy
Authorization: Bearer YOUR_TOKEN
```

The last path segment is the username, lowercase and URL-encoded. The `Authorization` header is sent only if you save a bearer token in the App. We recommend one, so only Namespace can call your adapter.

### Response

Return `200` with the profile for a user that exists, and `404` for one that doesn't.

```json
{
  "version": 1,
  "username": "happy",
  "texts": {
    "name": "Happy",
    "avatar": "https://cdn.brand.example/avatars/happy.png",
    "com.twitter": "happy"
  },
  "addresses": {
    "2147483648": "0xd8dA6BF26964aF9D7eEd9e03E53415D37aA96045",
    "0": "bc1qar0srrr7xfkvy5l643lydnw9re59gtzzwf5mdq",
    "501": "9WzDXwBbmkg8ZTbNMqUxvQRAyrZzDsGYdLVL9zYtAWWM"
  }
}
```

<ResponseField name="version" type="number" required>
  Always `1`.
</ResponseField>

<ResponseField name="username" type="string" required>
  The username from the request.
</ResponseField>

<ResponseField name="texts" type="Record<string, string>" required>
  Profile fields. Use [ENSIP-5](https://docs.ens.domains/ensip/5) keys such as `name`, `avatar`, `description`, `url`, `email` and `com.twitter`. Use `{}` for none.
</ResponseField>

<ResponseField name="addresses" type="Record<string, string>" required>
  Wallet addresses keyed by coin type. Use `{}` for none. See [Format addresses](#format-addresses).
</ResponseField>

<ResponseField name="contenthash" type="string">
  Optional. A website for the user, as an `ipfs://`, `ipns://` or `ar://` URI.
</ResponseField>

Don't add other top-level fields. The profile fails if you do.

### Format addresses

Each key in `addresses` is a coin type, written as a decimal string. It tells wallets which chain the address is for.

| Chain | Key | Why |
| --- | --- | --- |
| Every EVM chain (default) | `2147483648` | `0x80000000` in decimal, the ENS default EVM coin type |
| Ethereum mainnet | `60` | The [SLIP-44](https://github.com/satoshilabs/slips/blob/master/slip-0044.md) number for ETH |
| Base | `2147492101` | `0x80000000` plus Base's chain ID, `8453` |
| Bitcoin | `0` | SLIP-44 |
| Solana | `501` | SLIP-44 |

- **Most users need only `2147483648`.** It answers for Ethereum and every EVM chain that doesn't have its own key.
- **For a different address on one EVM chain**, add the key `0x80000000 | chainId`. viem's `toCoinType(chainId)` computes it for you.
- **For non-EVM chains**, use the chain's SLIP-44 number.

Return EVM addresses in checksum format (viem's `getAddress` does this) and Bitcoin addresses in their mainnet form. Namespace encodes them for ENS, so you send plain address strings.

### Example adapter

A Next.js route. Swap the database call for your own lookup.

```ts app/ens/[username]/route.ts
import { getAddress } from 'viem';
import { db } from '@/lib/db';

export async function GET(
  request: Request,
  { params }: { params: Promise<{ username: string }> },
) {
  const token = process.env.ENS_ADAPTER_TOKEN;
  const auth = request.headers.get('authorization');
  if (!token || auth !== `Bearer ${token}`) {
    return new Response(null, { status: 401 });
  }

  const { username } = await params;
  const user = await db.user.findUnique({ where: { username } });
  if (!user || !user.isPublic) {
    return new Response(null, { status: 404 });
  }

  const texts: Record<string, string> = {};
  if (user.displayName) texts.name = user.displayName;
  if (user.avatarUrl) texts.avatar = user.avatarUrl;

  const addresses: Record<string, string> = {};
  if (user.walletAddress) {
    addresses['2147483648'] = getAddress(user.walletAddress);
  }

  return Response.json({ version: 1, username, texts, addresses });
}
```

If your usernames live onchain, keep the same route and read the address from your registry contract instead of the database.

<Note>
**Adapter requirements.** HTTPS with a valid certificate, `application/json`, uncompressed, under 256 KiB, and a reply within 5 seconds. Redirects, `401`, `403`, `429` and `5xx` responses fail the lookup. Only `404` means the user doesn't exist.
</Note>

## Step 2: Save the adapter in the Namespace App

<Steps>
  <Step title="Open Universal Usernames">
    Go to [Universal Usernames](https://app.namespace.ninja/universal-usernames), connect the wallet that owns `brand.eth` and select the name.
  </Step>
  <Step title="Save the endpoint">
    Enter your base URL and, if you use one, your bearer token. Select **Save endpoint**.
  </Step>
  <Step title="Test a username">
    Enter a username that exists in your app and select **Test username**. The App shows what your adapter returned.
  </Step>
</Steps>

<Warning>
The test runs from your browser, so it shows **Blocked by CORS or unreachable** unless your adapter allows `https://app.namespace.ninja` (plus the `Authorization` header if you use a token). Real lookups come from the Namespace server, so CORS doesn't affect resolution. You can skip the test.
</Warning>

## Step 3: Set the resolver

Below your saved endpoint, the App walks you through up to three transactions:

<Steps>
  <Step title="Transfer records (optional)">
    Copies the records `brand.eth` has today, such as its address and avatar, to the new resolver so they keep resolving.
  </Step>
  <Step title="Set resolver">
    Points `brand.eth` at the Namespace resolver.
  </Step>
  <Step title="Enable Universal Usernames">
    Routes every subname of `brand.eth` to your adapter. The step reads **Resolver set and configured** when you're done.
  </Step>
</Steps>

<Warning>
A name serves one kind of subname at a time. If `brand.eth` already has offchain or L2 subnames, they stop resolving once you enable Universal Usernames.
</Warning>

That's it. `happy.brand.eth` now resolves with any ENS-compatible library or wallet, such as viem, ethers or wagmi, with no extra setup.

## Security practices

Your adapter decides where payments to your users go, so treat it like a payments API.

- **Use a bearer token** so only Namespace can call your adapter.
- **Return `404` for private, suspended or deleted accounts.** Anyone can guess a username and look it up.
- **Serve only addresses the user has proven they control**, for example by signing a message.
- **Don't reassign a released username right away.** Payments meant for the old user would go to the new one.
- **Protect the wallet that owns `brand.eth`** with a hardware wallet or multisig. Whoever controls it can redirect every username.

## Pros and cons

| Pros | Cons |
| --- | --- |
| Every existing user gets an ENS name at once, with nothing to mint | Users don't own the names onchain. Your system can rename or remove them |
| Your database stays the source of truth, with no syncing | If your adapter is down, names stop resolving. There's no fallback copy |
| No gas per user. Setup takes a few transactions on one name | A few apps don't support offchain (CCIP-Read) resolution yet |

## FAQ

<AccordionGroup>
  <Accordion title="Does this make my users' data public?">
    Only what your adapter returns. If people already see usernames, display names and avatars in your app, that data is public anyway. Exposing it through ENS doesn't change that. Leave out anything a user hasn't chosen to share.
  </Accordion>
  <Accordion title="How fast do profile changes show up?">
    Within 60 seconds. Namespace caches each profile for that long.
  </Accordion>
  <Accordion title="Can I use this if my usernames live onchain?">
    Yes. The adapter can read from a registry contract or an indexer instead of a database. The response format is the same.
  </Accordion>
  <Accordion title="My usernames allow uppercase or dots. Will they work?">
    ENS names are lowercase, and each username has to be a single label. Look users up by a lowercased copy of their username. Usernames with dots won't resolve.
  </Accordion>
  <Accordion title="Can I switch back later?">
    Yes. Point `brand.eth` at a different resolver at any time. Universal Usernames subnames stop resolving when you do.
  </Accordion>
</AccordionGroup>
