This guide makes your in-app usernames universal, so `happy` in your app becomes `happy.brand.eth` everywhere else. All you need is an ENS name. Setup takes three steps:

1. Build an API endpoint that returns a user's profile from your own data.
2. Save the endpoint in the Namespace App.
3. Set the resolver on your ENS name.

Your users don't sign up, mint or move anything. Every valid username you've issued works as soon as the resolver is set.

## Step 1: Build the API endpoint

The endpoint takes a username, reads that user from wherever your usernames live, such as a database, an API or a registry contract, and returns their public profile.

### Request

You choose a base URL, such as `https://api.brand.example/ens`. When someone looks up `happy.brand.eth`, your endpoint gets:

```http
GET https://api.brand.example/ens/happy
Authorization: Bearer YOUR_TOKEN
```

The last path segment is the username, normalized and URL-encoded. The `Authorization` header is sent only if you save a bearer token in step 2. We recommend one, so nobody else can call your endpoint.

### Response

Return `200` with the user's profile, or `404` if the user doesn't exist.

```json
{
  "version": 1,
  "username": "happy",
  "texts": {
    "name": "Happy",
    "avatar": "https://cdn.brand.example/avatars/happy.png",
    "com.twitter": "happy"
  },
  "addresses": {
    "2147483648": "0xd8dA6BF26964aF9D7eEd9e03E53415D37aA96045",
    "0": "bc1qar0srrr7xfkvy5l643lydnw9re59gtzzwf5mdq",
    "501": "9WzDXwBbmkg8ZTbNMqUxvQRAyrZzDsGYdLVL9zYtAWWM"
  }
}
```

| Field | Value |
| --- | --- |
| `version` | Always `1`. |
| `username` | The username from the request. |
| `texts` | Profile fields, as strings. See [Text records](#text-records). Use `{}` for none. |
| `addresses` | Wallet addresses by coin type. See [Addresses](#addresses). Use `{}` for none. |
| `contenthash` | Optional. A website for the user, such as `ipfs://…` or `ar://…`. |

Don't add other top-level fields. The profile fails if you do.

Before you write the endpoint, check that your usernames, text records and addresses fit the format below.

### Usernames

Each username becomes one ENS label, so it must pass [ENSIP-15](https://docs.ens.domains/ensip/15) normalization. Wallets normalize a name before looking it up, so your endpoint always receives the normalized form.

| Username | Result |
| --- | --- |
| `happy`, `happy-doe`, `123` | Works as is |
| `Happy`, `ＨＡＰＰＹ` | Works, as `happy` |
| `héllo`, `😀` | Works. Other scripts and emoji are valid |
| `_happy` | Works. Underscores are allowed only at the start |
| `happy_doe` | Invalid |
| `happy.doe` | Never reaches your endpoint. A dot splits it into two labels |
| `happy doe`, `@happy`, `happy!`, `happy+1` | Invalid. Spaces and most punctuation are disallowed |
| `ab--cd` | Invalid. No `--` in the third and fourth characters |

Normalization also rewrites some characters, such as `'` to `’`, and removes invisible ones. Store a normalized copy next to each username and look users up by that copy:

```ts
import { normalize } from 'viem/ens';

// Returns the ENS label for a username, or null if it can't be one.
export function toEnsLabel(username: string): string | null {
  try {
    const label = normalize(username);
    return label && !label.includes('.') ? label : null;
  } catch {
    return null;
  }
}
```

Users whose username returns `null` don't get an ENS name. If you're designing usernames from scratch, allowing only `a-z`, `0-9` and `-` means every username works.

### Text records

`texts` holds everything that isn't an address. Use the standard [ENSIP-5](https://docs.ens.domains/ensip/5) keys where they fit, since wallets and apps know how to show them:

| Key | Value |
| --- | --- |
| `name` | Display name |
| `avatar` | Image URL (`https://`, `ipfs://`) or an NFT as `eip155:1/erc721:0x…/1` |
| `description` | Short bio |
| `url` | Website |
| `email` | Email address |
| `com.twitter`, `com.github`, `org.telegram` | Handle on that service |

You can add your own keys too. Prefix them with your domain, such as `com.brand.tier` or `com.brand.member-since`, so they don't collide with anyone else's. Every value is a string, and a profile holds up to 128 text records.

### Addresses

Each key in `addresses` is a coin type, written as a decimal string. It tells wallets which chain the address belongs to.

| Chain | Key | Why |
| --- | --- | --- |
| Every EVM chain (default) | `2147483648` | `0x80000000` in decimal, the ENS default EVM coin type |
| Ethereum mainnet | `60` | The [SLIP-44](https://github.com/satoshilabs/slips/blob/master/slip-0044.md) number for ETH |
| Base | `2147492101` | `0x80000000` plus Base's chain ID, `8453` |
| Bitcoin | `0` | SLIP-44 |
| Solana | `501` | SLIP-44 |

- **Most users need only `2147483648`.** It answers for Ethereum and every EVM chain that doesn't have its own key.
- **For a different address on one EVM chain**, add the key `0x80000000 | chainId`. viem's `toCoinType(chainId)` computes it for you.
- **For non-EVM chains**, use the chain's SLIP-44 number.

Send plain address strings, not encoded bytes. EVM addresses go in checksum format (viem's `getAddress`), and Bitcoin addresses in their mainnet form.

### Example endpoint

A Next.js route. Swap the database call for your own lookup.

```ts app/ens/[username]/route.ts
import { getAddress } from 'viem';
import { db } from '@/lib/db';

export async function GET(
  request: Request,
  { params }: { params: Promise<{ username: string }> },
) {
  const token = process.env.ENS_ADAPTER_TOKEN;
  const auth = request.headers.get('authorization');
  if (!token || auth !== `Bearer ${token}`) {
    return new Response(null, { status: 401 });
  }

  const { username } = await params;
  // ensLabel is the normalized copy from toEnsLabel.
  const user = await db.user.findUnique({ where: { ensLabel: username } });
  if (!user || !user.isPublic) {
    return new Response(null, { status: 404 });
  }

  const texts: Record<string, string> = {};
  if (user.displayName) texts.name = user.displayName;
  if (user.avatarUrl) texts.avatar = user.avatarUrl;

  const addresses: Record<string, string> = {};
  if (user.walletAddress) {
    addresses['2147483648'] = getAddress(user.walletAddress);
  }

  return Response.json({ version: 1, username, texts, addresses });
}
```

If your usernames live onchain, keep the same route and read from your registry contract instead of the database.

<Note>
The endpoint must use HTTPS with a valid certificate, return uncompressed `application/json` under 256 KiB, and reply within 5 seconds. Redirects, `401`, `403`, `429` and `5xx` responses fail the lookup. Only `404` means the user doesn't exist.
</Note>

## Step 2: Save the endpoint in the Namespace App

<Steps>
  <Step title="Open Universal Usernames">
    Go to [Universal Usernames](https://app.namespace.ninja/universal-usernames), connect the wallet that owns `brand.eth` and select the name.
  </Step>
  <Step title="Save the endpoint">
    Enter your base URL and, if you use one, your bearer token. Select **Save endpoint**.
  </Step>
  <Step title="Test a username">
    Enter a username that exists in your app and select **Test username**. The App shows what your endpoint returned.
  </Step>
</Steps>

<Warning>
The test runs from your browser, so it shows **Blocked by CORS or unreachable** unless your endpoint allows `https://app.namespace.ninja` (plus the `Authorization` header if you use a token). Real lookups don't come from a browser, so CORS doesn't affect resolution. You can skip the test.
</Warning>

## Step 3: Set the resolver

This is the step that makes your usernames live. Below your saved endpoint, the App walks you through up to three transactions:

<Steps>
  <Step title="Transfer records (optional)">
    Copies the records `brand.eth` has today, such as its address and avatar, to the new resolver so they keep resolving.
  </Step>
  <Step title="Set resolver">
    Points `brand.eth` at the Namespace resolver.
  </Step>
  <Step title="Enable Universal Usernames">
    Routes every subname of `brand.eth` to your endpoint. The step reads **Resolver set and configured** when you're done.
  </Step>
</Steps>

<Warning>
A name serves one kind of subname at a time. If `brand.eth` already has offchain or L2 subnames, they stop resolving once you enable Universal Usernames.
</Warning>

That's it. `happy.brand.eth` now resolves outside your app, in any wallet or library that supports ENS, such as viem, ethers or wagmi.

## Security practices

Your endpoint decides where payments to your users go, so treat it like a payments API.

- **Use a bearer token** so nobody else can call your endpoint.
- **Return `404` for private, suspended or deleted accounts.** Anyone can guess a username and look it up.
- **Serve only addresses the user has proven they control**, for example by signing a message.
- **Don't reassign a released username right away.** Payments meant for the old user would go to the new one.
- **Protect the wallet that owns `brand.eth`** with a hardware wallet or multisig. Whoever controls it can redirect every username.

## FAQ

<AccordionGroup>
  <Accordion title="Does this make my users' data public?">
    Only what your endpoint returns. If people already see usernames, display names and avatars in your app, that data is public anyway, and showing it through ENS doesn't change that. Leave out anything a user hasn't chosen to share.
  </Accordion>
  <Accordion title="How fast do profile changes show up?">
    Usually right away. A profile is cached for at most a minute, so an edit can take up to that long to reach wallets.
  </Accordion>
  <Accordion title="Can I use this if my usernames live onchain?">
    Yes. The endpoint can read from a registry contract or an indexer instead of a database. The response format is the same.
  </Accordion>
  <Accordion title="Some of my usernames have underscores, dots or symbols. What happens to them?">
    They don't get an ENS name. The rest of your users still do. See [Usernames](#usernames) for what's valid.
  </Accordion>
  <Accordion title="Can I switch back later?">
    Yes. Point `brand.eth` at a different resolver at any time. Universal Usernames subnames stop resolving when you do.
  </Accordion>
</AccordionGroup>
