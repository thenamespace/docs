This guide walks you through building the one endpoint Universal Usernames needs, then connecting it to your ENS name. When you're done, `happy` in your app resolves as `happy.brand.eth` in any ENS-aware wallet.

The endpoint is a small HTTP service. It takes a username, reads that user from wherever your usernames live, and returns a profile in the format below. Where they live doesn't matter: a database behind your app, or a registry contract if you run a naming service. For why this works and what to decide first, read the [Universal usernames overview](/overview/universal-usernames).

## Prerequisites

- An ENS name such as `brand.eth`, owned by a wallet you control.
- Somewhere to host a public HTTPS route.
- Usernames that are valid [ENSIP-15](https://docs.ens.domains/ensip/15) labels: lowercase, no dots. If yours allow uppercase, match against a lowercased copy.

## Step 1: Build the endpoint

### The request

You pick a base URL, such as `https://api.brand.example/ens`. For `happy.brand.eth`, the Namespace gateway sends:

```http
GET /ens/happy HTTP/1.1
Host: api.brand.example
Accept: application/json
Accept-Encoding: identity
Authorization: Bearer YOUR_TOKEN
```

- The last path segment is the username, URL-encoded and already normalized. Decode it before you look it up.
- `Authorization` is only sent if you save a bearer token in the App.
- Only single labels reach you. Nested names like `a.happy.brand.eth` never call your endpoint.

### The response

Return `200` with this JSON for a user that exists, and `404` for one that doesn't:

```json happy.json
{
  "version": 1,
  "username": "happy",
  "texts": {
    "name": "Happy",
    "avatar": "https://cdn.brand.example/avatars/happy.png",
    "com.twitter": "happy"
  },
  "addresses": {
    "2147483648": "0xd8dA6BF26964aF9D7eEd9e03E53415D37aA96045",
    "0": "bc1qar0srrr7xfkvy5l643lydnw9re59gtzzwf5mdq",
    "501": "9WzDXwBbmkg8ZTbNMqUxvQRAyrZzDsGYdLVL9zYtAWWM"
  }
}
```

<ResponseField name="version" type="number" required>
  Always the number `1`.
</ResponseField>

<ResponseField name="username" type="string" required>
  The requested username, exactly as it arrived after decoding.
</ResponseField>

<ResponseField name="texts" type="Record<string, string>" required>
  [ENSIP-5](https://docs.ens.domains/ensip/5) text records such as `name`, `avatar`, `description`, `url` and `com.twitter`. Use `{}` for none.
</ResponseField>

<ResponseField name="addresses" type="Record<string, string>" required>
  Addresses keyed by ENS coin type as a decimal string. Use `{}` for none. See [Address keys](#address-keys).
</ResponseField>

<ResponseField name="contenthash" type="string">
  Optional. An `ipfs://`, `ipns://`, `ar://` or other [ENSIP-7](https://docs.ens.domains/ensip/7) URI. Leave it out when there is none.
</ResponseField>

Any other top-level field fails the profile.

### Address keys

- `2147483648` is the default EVM address. It answers for Ethereum and every EVM chain without its own key, so most users need only this one.
- Add `0x80000000 | chainId` for a chain where the address differs. Base (`8453`) is `2147492101`. viem's `toCoinType(chainId)` does the math.
- Non-EVM chains use their [SLIP-44](https://github.com/satoshilabs/slips/blob/master/slip-0044.md) number: Bitcoin is `0`, Solana is `501`.
- Return EVM addresses checksummed. Bitcoin addresses must be mainnet.

### Example endpoint

This route uses web-standard `Request` and `Response`, so it runs as a Next.js App Router route (`app/ens/[label]/route.ts`) or in any server that speaks Fetch. Swap `findUserByUsername` for your own lookup.

```ts route.ts
import { timingSafeEqual } from 'node:crypto';
import { getAddress } from 'viem';
import { findUserByUsername } from './users';

const BEARER_TOKEN = process.env.UUN_BEARER_TOKEN;
const DEFAULT_EVM_COIN_TYPE = '2147483648';

function isAuthorized(request: Request): boolean {
  if (!BEARER_TOKEN) return true;
  const expected = Buffer.from(`Bearer ${BEARER_TOKEN}`);
  const received = Buffer.from(request.headers.get('authorization') ?? '');
  return (
    received.length === expected.length && timingSafeEqual(received, expected)
  );
}

// GET {base URL}/{username}
export async function GET(request: Request): Promise<Response> {
  if (!isAuthorized(request)) return new Response(null, { status: 401 });

  const segment = new URL(request.url).pathname.split('/').pop() ?? '';
  let username: string;
  try {
    username = decodeURIComponent(segment);
  } catch {
    return new Response(null, { status: 404 });
  }

  const user = await findUserByUsername(username);
  if (!user) return new Response(null, { status: 404 });

  // Anyone can read these, so publish only what the user chose to share.
  const texts: Record<string, string> = {};
  if (user.displayName) texts.name = user.displayName;
  if (user.avatarUrl) texts.avatar = user.avatarUrl;

  const addresses: Record<string, string> = {};
  if (user.walletAddress) {
    addresses[DEFAULT_EVM_COIN_TYPE] = getAddress(user.walletAddress);
  }

  return Response.json({ version: 1, username, texts, addresses });
}
```

```ts users.ts

  avatarUrl?: string;
  walletAddress?: string;
};
```

### If your usernames live onchain

Running a naming service with its own registry? Keep the same route and read the user from your contract instead. This version of `findUserByUsername` reads the address with viem. Replace the ABI and function with your registry's own lookup.

```ts users.ts
import { createPublicClient, http, parseAbi, zeroAddress } from 'viem';

const client = createPublicClient({ transport: http(process.env.RPC_URL) });

const REGISTRY_ADDRESS = process.env.REGISTRY_ADDRESS as `0x${string}`;
const REGISTRY_ABI = parseAbi([
  'function resolve(string name) view returns (address)',
]);

export type User = {
  displayName?: string;
  avatarUrl?: string;
  walletAddress?: string;
};

export async function findUserByUsername(username: string): Promise<User | null> {
  const walletAddress = await client.readContract({
    address: REGISTRY_ADDRESS,
    abi: REGISTRY_ABI,
    functionName: 'resolve',
    args: [username],
  });
  if (walletAddress === zeroAddress) return null;
  return { walletAddress };
}
```

Every lookup hits your RPC, so use a reliable provider. The gateway caches each profile for 60 seconds.

### Test it

```bash
curl -i https://api.brand.example/ens/happy -H 'Authorization: Bearer YOUR_TOKEN'
```

Expect `200`, `content-type: application/json` and `"username": "happy"`. An unknown username should return `404`.

### Rules the gateway enforces

The gateway fails the lookup instead of guessing, so check these before you go live:

- The base URL is `https://`, with no query string or fragment, up to 2048 characters.
- The host resolves to public IPs only and has a valid TLS certificate.
- The response is `application/json`, uncompressed, at most 256 KiB, and arrives within 5 seconds.
- Redirects, `401`, `403`, `429` and `5xx` all fail the lookup. Only `404` means "no such user".
- At most 128 text records and 128 addresses.

  <Step title="Save the endpoint">

  </Step>
  <Step title="Check a few usernames">
    Enter a real username and select **Check endpoint**. The check runs in your browser, so allow `https://app.namespace.ninja` with CORS (plus `Access-Control-Allow-Headers: Authorization` if you use a token). It's optional.
  </Step>
  <Step title="Set the resolver">
    Send the transaction the App shows. When it reads **Resolver set and configured**, every `username.brand.eth` resolves from your endpoint.
  </Step>
</Steps>

<Warning>
A name serves one kind of subname at a time. If `brand.eth` already serves offchain or L2 subnames, those stop resolving once you switch.
</Warning>

Profile changes reach wallets within 60 seconds. A new endpoint or token takes effect within about 5 seconds.

## Before you go live

Your endpoint now decides where payments to your users go.

- Return `404` for private, suspended or deleted accounts. Anyone can guess usernames.
- Serve only addresses the user has proven they control.
- Don't hand a released username to someone new right away, or payments meant for the old user go to them.
- Require a bearer token, and keep the wallet that owns `brand.eth` on a hardware wallet or multisig.
